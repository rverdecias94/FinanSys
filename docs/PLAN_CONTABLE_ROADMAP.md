# PLAN — Roadmap contable profesional (Cuba-first, base extensible)

> Objetivo: dar a GESTIA **bases profesionales** de gestión financiera **sin convertirlo
> en un ERP complejo**. Diseñado para la **realidad cubana** (efectivo, informal, sin
> integración ni facturación bancaria) pero **sentando cimientos** para escalar fuera el día
> de mañana (otros países, impuestos, e-factura, consolidación).
>
> Estado: **PLAN (sin código)**. Para ejecutar **por sesiones**. Basado en el esquema real
> verificado en Supabase. Fecha: **2026-06-19**.

---

## 0. Contexto real y principios rectores

**Realidad del cliente (Cuba):**
- Casi todo es **efectivo**; las operaciones bancarias son poco comunes y muchas informales.
- La PYME gestiona desde casa/negocio, **sin integración bancaria ni facturación electrónica**.
- Multimoneda de facto: **USD, CUP, MLC/EUR, MXN** con tipos de cambio **informales y volátiles**.

**Principios de diseño (no negociables):**
1. **Caja primero.** Todo nace como efectivo; el "banco" es **opcional**, nunca obligatorio.
2. **Sin integración bancaria ni e-factura obligatoria.** Solo registro manual y comprobantes PDF simples.
3. **Extender, no reescribir.** Se amplía el modelo de caja actual (`transactions`); **no** se migra a
   partida doble ni plan de cuentas. Eso mantiene la simplicidad para el usuario no técnico.
4. **Campos profesionales presentes pero opcionales.** Impuesto, contacto, vencimiento, cuenta…
   existen en el modelo pero con **defaults que los hacen invisibles en Cuba** (impuesto 0, cuenta
   "Efectivo"). Así la base ya es "profesional" sin estorbar.
5. **Extensibilidad por configuración, no por reescritura.** La jurisdicción (impuestos, formato,
   e-factura) se resuelve con `business_settings.region` + adaptadores futuros, no tocando el core.
6. **Discreción.** Dado el contexto, reforzar privacidad (RLS ya existe, offline ya existe; añadir
   opción de **ocultar montos / bloqueo por PIN** como mejora ligera).
7. **Convenciones del repo:** PK `bigint generated by default as identity`,
   `user_id uuid default get_current_business_id()`, **RLS activado** con política
   `user_id = get_current_business_id()`, `created_at timestamptz default now()`.

## Fase 1 — Contactos + Cuentas por cobrar/pagar (CxC/CxP) · **mayor valor**

**Qué resuelve:** saber *quién me debe, a quién le debo y qué está vencido*. Hoy no existe
(no hay tablas `contacts`/`customers`/`suppliers`).

**Migraciones:**
- **`contacts`** — clientes y proveedores en una sola tabla:
  ```
  id bigint identity PK
  user_id uuid default get_current_business_id()
  name text not null
  kind text check (kind in ('cliente','proveedor','ambos')) default 'cliente'
  phone text, email text, notes text
  is_active boolean default true
  created_at timestamptz default now(), updated_at timestamptz default now()
  ```
  RLS por `user_id`. Índice `(user_id, name)`.
- **Extender `transactions`** (no tabla nueva → mantiene simple):
  ```
  contact_id   bigint null references contacts(id)
  status       text check (status in ('paid','pending','partial')) default 'paid'
  due_date     timestamptz null
  paid_amount  numeric default 0
  ```
  Una venta a crédito = `income` con `status='pending'` + `due_date`. Al cobrar se actualiza
  `paid_amount`/`status` (con registro en auditoría). **CxC = income pendiente; CxP = expense pendiente.**

**UI/servicios:** sección **Contactos** (listado `ResponsiveListing`); en `TransactionModal`, selector de
contacto + estado (pagado/pendiente) + vencimiento (todo opcional); vista **"Por cobrar / Por pagar"**
con **antigüedad de saldos** (vencido / por vencer). Picker premium ya disponible para `due_date`.

**Cuba vs. escalar:** en Cuba se usa poco al inicio (todo "pagado/efectivo"), pero la base queda
lista. Fuera, habilita cobranza/crédito real.

**Esfuerzo:** **M** (1 migración + 1 sección nueva + cambios en modal y un reporte). ~2 sesiones.

## Fase 2 — SKU / código de barras en Almacén (+ base para escáner)

**Qué resuelve:** inconsistencia verificada — el **Inventario dinámico** ya tiene `sku` con
autogeneración (`inventory_area_prefixes.prefix/next_seq`), pero **`products` (Almacén) no tiene código**.

**Migración:**
```
alter table products add column sku text null;
alter table products add column barcode text null;
create unique index on products (user_id, barcode) where barcode is not null;
```
Generador de SKU: reutilizar el patrón prefijo+secuencia ya existente (RPC `next_sku(prefix)` o
tabla análoga a `inventory_area_prefixes`).

**UI/servicios:** en `ProductModal`, campos SKU/código + botón "Generar SKU"; `ProductList` muestra SKU;
búsqueda por SKU/código.

**Cuba vs. escalar:** útil ya (orden interno); imprescindible para retail/escala.

**Esfuerzo:** **S-M**. ~1 sesión.

## Fase 3 — Cuentas de efectivo/banco (opcional, ya medio cableado)

**Qué resuelve:** `transactions.details.bank_account_id` existe pero **siempre null y sin tabla**.
Separar saldos por "caja" y, opcionalmente, "banco".

**Migraciones:**
- **`accounts`**:
  ```
  id bigint identity PK
  user_id uuid default get_current_business_id()
  name text not null
  type text check (type in ('cash','bank')) default 'cash'
  currency_code text references currencies(code)
  opening_balance numeric default 0
  is_active boolean default true
  created_at timestamptz default now()
  ```
- `transactions.account_id bigint null references accounts(id)` (reemplaza el `bank_account_id` huérfano).
- Seed: una cuenta **"Efectivo"** por moneda al crear negocio → en Cuba el usuario nunca "ve" cuentas si no quiere.

**Cuba vs. escalar:** Cuba = solo "Efectivo" (transparente). Fuera = múltiples cuentas/bancos + base para conciliación.

**Esfuerzo:** **M**. ~1-2 sesiones.

## Fase 4 — Impuesto opcional + comprobante simple (PDF)

**Qué resuelve:** no hay impuestos (solo "Impuestos" como categoría). Dejar la **base fiscal** sin
imponerla en Cuba.

**Migraciones / config:**
- `transactions.tax_rate numeric default 0`, `tax_amount numeric default 0`.
- `business_settings.region` → añadir `{ taxLabel: 'Impuesto', defaultTaxRate: 0 }` (Cuba: 0 → invisible).
- **Comprobante**: generar **PDF simple** desde una transacción/venta (reutiliza la infra de export ya
  existente) + **folio** correlativo opcional (`documents` o un contador). **No** e-factura.
- Base para e-factura futura: `document_type`, `external_ref` (vacíos hoy) → un adaptador por país
  podría llenarlos sin tocar el core.

**Cuba vs. escalar:** Cuba = impuesto 0, comprobante PDF informal. México u otros = IVA + e-factura
vía adaptador (CFDI/SAT, etc.), sin reescribir.

**Esfuerzo:** **M**. ~1-2 sesiones.

## Fase 5 — Venta → stock → COGS (integridad de inventario) · *opcional/avanzado*

**Qué resuelve:** hoy vender no descuenta stock ni registra **costo de ventas**; `valuation_method='fifo'`
es **cosmético** (movimientos no guardan costo).

**Migraciones:**
- `movements.unit_cost numeric null` (capturar costo por movimiento).
- Recomendado: **costo promedio ponderado** (simple y defendible) en vez de FIFO con capas; actualizar
  `business_settings.valuation_method` por defecto a `'average'`.
- Enlazar venta (income de tipo producto) ↔ salida de stock ↔ COGS (modo "inventario contable", activable).

**Cuba vs. escalar:** activable; aporta utilidad real por producto.

**Esfuerzo:** **L** (el más complejo). Dejar para el final.

## Fase 6 — Multimoneda con moneda base + tipo de cambio + consolidación

**Qué resuelve:** hay 4 monedas activas pero **sin tipos de cambio** y los informes reportan por
moneda separada (el propio informe lo advierte). Sin consolidar no hay "patrimonio/resultado" único.

**Migraciones / config:**
- **`exchange_rates`**: `user_id, currency_code, rate_to_base numeric, effective_date date, created_at`
  (carga **manual** — encaja con tasas informales cubanas).
- `business_settings.region.baseCurrency` (p. ej. USD).
- Informes: vista consolidada a moneda base usando la tasa vigente; **mantener** también la vista por moneda.

**Cuba vs. escalar:** crítico en Cuba por USD↔CUP↔MLC; igual de útil fuera.

**Esfuerzo:** **M**. ~1-2 sesiones.

## Fase 7 — Recurrentes + cierre de período

**Qué resuelve:** nómina/renta/suscripciones se repiten (ya registras "Nómina"); y el pasado es
editable sin candado.

**Migraciones:**
- **`recurring_transactions`**: plantilla (tipo, monto, moneda, categoría, contacto, cuenta) + `frequency`
  (`monthly`/`weekly`…) + `next_run date`. Generación al abrir la app o vía función programada.
- **Cierre**: `business_settings.closed_through date` (o tabla `closed_periods`); **bloquear edición**
  de transacciones anteriores (guard en app + idealmente policy RLS).

**Esfuerzo:** **M**. ~1-2 sesiones.

## Fase 8 — Estados financieros + resumen fiscal

**Qué resuelve:** hoy solo Estado de Resultados (base caja). Faltan **Flujo de Efectivo** y un
**resumen de impuestos**; el Balance General real requiere más estructura.

**Alcance:**
- **Estado de Flujo de Efectivo** (entradas/salidas por período y cuenta).
- **Resumen de impuestos** (usando `tax_amount`), exportable.
- **"Posición" simplificada** (saldos de cuentas + por cobrar − por pagar) en lugar de Balance General formal.

**Esfuerzo:** **M**. ~1 sesión (depende de Fases 1, 3, 4).

## Cómo estas bases permiten "salir de Cuba" sin reescribir

- **Jurisdicción por configuración:** `business_settings.region` decide etiqueta de impuesto, tasa,
  formato y (futuro) e-factura. El core no cambia.
- **Impuesto/contacto/cuenta/folio ya en el modelo** (con defaults neutros) → activar funciones de
  otro país es "encender", no "construir".
- **E-factura como adaptador** (CFDI/SAT u otros) sobre `document_type`/`external_ref`, aislado del core.
- **Moneda base + tipos de cambio** sirven igual para cualquier mercado multimoneda.

## Lo que seguimos evitando (para no complejizar)
- Partida doble / plan de cuentas / libro mayor formal.
- Integración bancaria automática (bank feeds) y e-factura real (hasta que un mercado lo exija).
- Balance General contable formal (usamos "posición" simplificada).
